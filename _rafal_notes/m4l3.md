## Prompt do /10x-research

/10x-research use-app-state-flow Przeanalizuj przepływ stanu aplikacji dotcom przez `useAppState`, zwracając szczególną uwagę na powiązane z nim obszary zdefiniowane w `context/map/repo-map.md`.

Cel analizy:
Zrozumieć, jak `useAppState` skleja aplikację tldraw.com z edytorem, workspace/file state, auth, sync/multiplayer oraz komponentami UI — i gdzie ten przepływ jest kruchy, trudny do testowania albo ma duży blast radius.

Wykorzystaj trzech równoległych sub-agentów:

1. Trace e2e:
   Odtwórz ścieżkę od wejścia użytkownika w dotcom UI / workspace / `TlaEditor.tsx`, przez `useAppState`, zależności file/auth/sync/workspace state, aż do miejsc, gdzie stan trafia do komponentów UI, Editora albo SDK.

Pokaż:

- główne entry pointy z `file:line`
- sekwencję kroków przepływu danych/stanu
- co jest źródłem stanu
- co jest stanem pochodnym
- które callbacki/metody zmieniają stan
- gdzie przepływ przekracza granicę dotcom app → editor / tldraw SDK
- diagram Mermaid pokazujący przepływ

Nie opisuj tylko listy plików. Odtwórz realny przepływ.

2. Luki w testach:
   Sprawdź, które części ścieżki `useAppState` mają pokrycie testami, a które nie.

Szczególnie sprawdź:

- czy istnieje `TestAppState`, test provider, factory, mock albo fixture dla app state
- czy komponenty konsumujące `useAppState` da się testować bez mockowania całego stacku dotcom
- czy testowane są ścieżki auth/file/sync/workspace
- czy testowane są error branches i edge cases
- czy testy są unit/component/e2e/integration
- gdzie testy zależą od realnego Editora, sync albo zewnętrznego środowiska

Oddziel:

- realne testy jednostkowe
- testy komponentowe
- testy e2e
- mocki
- brakujące ścieżki
- unknowns

3. Blast radius:
   Sprawdź, co musi zmienić się razem przy zmianie `useAppState`.

Uwzględnij:

- direct consumers `useAppState`
- komponenty zależne od konkretnych pól zwracanych przez hook
- zależności file/auth/sync/workspace
- wpływ na `TlaEditor.tsx`
- wpływ na editor / SDK boundary
- wpływ na testy
- wpływ na typy/model stanu
- wpływ na dotcom client
- potencjalny wpływ na sync-worker / multiplayer, jeśli jest widoczny w kodzie albo historii gita

Połącz:

- graf statyczny / importy
- wyszukiwanie call-site’ów
- co-change z historii gita, jeśli to możliwe

Skup się wyłącznie na analizie i opisie obecnego stanu repozytorium.

Nie proponuj jeszcze refaktoru.
Nie projektuj nowej architektury.
Nie zmieniaj kodu.
Nie rób rewrite.
Nie naprawiaj testów.

Raport musi zawierać dwie jawne sekcje:

1. Feature overview
2. Technical debt

W raporcie oddziel:

- evidence — potwierdzone w kodzie, z `file:line`
- inference — interpretacja na podstawie dowodów
- unknown — rzeczy niepotwierdzone albo wymagające dalszego sprawdzenia

W sekcji `Feature overview` pokaż:

- skąd wchodzi przepływ
- jak dane/stany przepływają przez `useAppState`
- kto konsumuje wynik hooka
- które pola/metody są najważniejsze
- gdzie realnie zmienia się stan
- gdzie stan przechodzi do Editora / SDK / sync

W sekcji `Technical debt` pokaż:

- kruche sprzężenia
- brakujące testy
- god-hook symptoms
- miejsca o dużym blast radius
- dynamiczne sprzężenia niewidoczne w importach
- obszary, które wyglądają groźnie, ale są tanie/mechaniczne
- obszary, których nie dało się potwierdzić

## ulepszamy raport ast grep

Ulepszamy raport `context/changes/use-app-state-flow/research.md`.

Najpierw wypisz z niego wszystkie twierdzenia STRUKTURALNE, czyli:

- liczby call-site'ów
- liczby konsumentów `useAppState`
- twierdzenia typu "tylko tutaj"
- twierdzenia typu "zawsze przez X"
- liczność metod / callbacków / pól zwracanych przez hook
- powtarzające się kształty wywołań
- informacje o tym, gdzie używany jest `useAppState`
- informacje o tym, gdzie `useAppState` jest importowany, wywoływany, mockowany albo re-exportowany
- informacje o komponentach zależnych od konkretnych pól zwracanych przez `useAppState`
- informacje o zależnościach hooka od file/auth/sync/workspace/editor state
- informacje o testach, mockach, providerach, fixture’ach albo braku `TestAppState`

Dla każdego twierdzenia zbuduj wzorzec `ast-grep` odpowiedni dla języka w repozytorium.

Repozytorium tldraw jest głównie TypeScript / TSX, więc używaj wzorców dla `ts` i `tsx`.

Przykładowe obszary do sprawdzenia:

- wywołania `useAppState($$$A)`
- importy `useAppState`
- destrukturyzacje wyniku hooka
- użycia pól zwracanych przez hook
- komponenty zależne od hooka
- mocki typu `vi.mock`, `jest.mock`, `mockUseAppState`
- test helpery, providery, fixture’y
- ewentualne re-exporty albo barrel files

Następnie wywołaj `ast-grep` i przeanalizuj wyniki.

Wynik podaj jako:

`twierdzenie -> potwierdzone / doprecyzowane / obalone / nadal unknown`

Dla każdego wyniku dodaj dokładne pliki i linie.

Każde zero z `ast-grep` potwierdź klasycznym `rg` albo `grep`, żeby odróżnić realny brak wystąpień od złego wzorca.

Szczególnie sprawdź:

## 1. Konsumenci `useAppState`

Zweryfikuj, ile jest realnych konsumentów `useAppState`.

Oddziel:

- runtime consumers
- test consumers
- re-exporty / barrel files
- komentarze
- martwe odniesienia
- false positives z tekstowego wyszukiwania

Nie zakładaj, że liczba z raportu jest poprawna. Potwierdź ją narzędziowo.

## 2. Importy i call-site’y

Sprawdź wszystkie miejsca, które importują albo wywołują `useAppState`.

Dla każdego wyniku ustal:

- czy to realny call-site
- czy tylko import
- czy hook jest wywoływany bezpośrednio w komponencie
- czy wynik hooka jest przekazywany dalej
- czy używana jest destrukturyzacja
- czy używany jest cały zwracany obiekt

## 3. Kształt kontraktu `useAppState`

Sprawdź, od których konkretnych pól/metod zwracanych przez `useAppState` zależą konsumenci.

Szukaj wzorców typu:

- `const { $$$FIELDS } = useAppState($$$A)`
- `const $X = useAppState($$$A)`
- `$X.$FIELD`
- przekazywanie wyniku hooka jako props
- callbacki albo metody zwracane przez hook

Celem jest ustalenie, czy zmiana return object `useAppState` ma szeroki blast radius.

## 4. Zależności hooka

Sprawdź, co `useAppState` importuje, wywołuje albo łączy.

Szczególnie szukaj powiązań z:

- file state
- auth / user / session
- sync / multiplayer
- workspace
- editor / SDK
- routing
- persistence / storage
- dotcom client state

Oznacz, które zależności są potwierdzone w kodzie, a które były tylko inference w raporcie.

## 5. Testability gap

Sprawdź, czy istnieje `TestAppState`, test provider, factory, mock albo fixture związany z `useAppState`.

Użyj zarówno `ast-grep`, jak i `rg`, bo nazwy helperów testowych mogą nie pasować do jednego wzorca AST.

Szukaj m.in.:

- `TestAppState`
- `mockUseAppState`
- `useAppState.mock`
- `vi.mock`
- `jest.mock`
- `createAppState`
- `AppStateProvider`
- `TestProvider`
- fixture setup dla dotcom app state
- testy komponentów konsumujących `useAppState`

Oceń, czy twierdzenie "brak TestAppState" jest:

- potwierdzone
- doprecyzowane, bo istnieją częściowe mocki/helpery
- obalone
- nadal unknown

Podziel je na:

- direct consumers

- file/auth/sync/workspace dependencies
